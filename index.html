Cargar un CSV a Snowflake y limpiarlo

Lo uso en mi trabajo

Problema

Tienes un CSV en tu computador y necesitas una tabla confiable en Snowflake, sin que un valor malo detenga toda la carga.

Conceptos

  • Stage: un lugar donde Snowflake recibe archivos antes de cargarlos.
  • COPY INTO: el comando que mueve el archivo del stage a una tabla.
  • TRY_TO_*: convierten tipos y devuelven NULL si falla, en vez de romper la consulta.

Diagrama

CSV local --PUT--> STAGE --COPY INTO--> tabla bronze --CREATE TABLE AS--> tabla silver

Ejemplo

Cargo todo como texto a una tabla bronze y convierto fechas y montos en la tabla silver. Los registros con error quedan en NULL y los puedo revisar.

Código

CREATE OR REPLACE FILE FORMAT ff_csv
  TYPE = CSV SKIP_HEADER = 1 FIELD_OPTIONALLY_ENCLOSED_BY = '"';

CREATE OR REPLACE STAGE stg_ventas FILE_FORMAT = ff_csv;
-- Desde SnowSQL:  PUT file://ventas.csv @stg_ventas;

CREATE OR REPLACE TABLE bronze_ventas
  (id_venta STRING, fecha STRING, pais STRING, monto STRING);

COPY INTO bronze_ventas FROM @stg_ventas ON_ERROR = 'CONTINUE';

CREATE OR REPLACE TABLE silver_ventas AS
SELECT DISTINCT
  id_venta,
  TRY_TO_DATE(fecha)           AS fecha,
  pais,
  TRY_TO_NUMBER(monto, 18, 2)  AS monto
FROM bronze_ventas
WHERE id_venta IS NOT NULL;

Qué deberías ver

COPY INTO devuelve una fila por archivo con rows_loaded y errors_seen.
SELECT COUNT(*) FROM silver_ventas;  -- menos filas que bronze_ventas

Revisa errors_seen: si no es cero, mira cuáles filas fallaron antes de confiar en la tabla.

Errores comunes

  • Usar ON_ERROR = 'CONTINUE' y no revisar cuántos errores hubo.
  • Cargar directo con tipos estrictos: una fecha mala detiene toda la carga.
  • Olvidar el SKIP_HEADER y cargar el encabezado como dato.

Referencias

  • COPY INTO table (Snowflake docs)
  • Overview of data loading (Snowflake docs)

Arquitectura Medallion en Fabric

Lo uso en mi trabajo

Problema

Un archivo crudo trae duplicados, fechas como texto y montos mal escritos. Si lo conectas directo a un reporte, cada cifra queda en duda.

Conceptos

  • Bronze: el dato tal como llegó, sin arreglar. Es tu respaldo.
  • Silver: limpio, con tipos correctos y sin duplicados.
  • Gold: agregado y listo para el negocio o para Power BI.
  • En Fabric las tres capas suelen ser tablas Delta en un Lakehouse.

Diagrama

CSV / API  →  BRONZE (crudo)  →  SILVER (limpio)  →  GOLD (agregado)  →  Power BI
                  append       reglas de calidad     reglas de negocio

Ejemplo

Ventas en CSV con id_venta repetido y monto como texto. Bronze lo guarda igual, Silver lo corrige y Gold suma las ventas por día y país.

Código

# Notebook de Fabric (PySpark). Ejemplo didáctico.
from pyspark.sql import functions as F

# BRONZE: guardar tal cual llega
raw = spark.read.option("header", True).csv("Files/ventas.csv")
raw.write.mode("append").format("delta").saveAsTable("bronze_ventas")

# SILVER: tipos, nulos y duplicados
silver = (spark.table("bronze_ventas")
    .filter(F.col("id_venta").isNotNull())
    .dropDuplicates(["id_venta"])
    .withColumn("fecha", F.to_date("fecha"))
    .withColumn("monto", F.col("monto").cast("decimal(18,2)")))
silver.write.mode("overwrite").format("delta").saveAsTable("silver_ventas")

# GOLD: lo que consume el negocio
gold = silver.groupBy("fecha", "pais").agg(F.sum("monto").alias("ventas"))
gold.write.mode("overwrite").format("delta").saveAsTable("gold_ventas_dia_pais")

Qué deberías ver

bronze_ventas : 1.000 filas (con duplicados)
silver_ventas : 962 filas (sin duplicados ni nulos)
gold_ventas_dia_pais : 1 fila por fecha y país

Las cifras son de ejemplo: lo importante es que Silver tenga menos filas que Bronze y que puedas explicar la diferencia.

Errores comunes

  • Limpiar los datos en Bronze: pierdes la copia original.
  • Sobrescribir Bronze en cada carga: pierdes el historial.
  • No definir la llave única antes de quitar duplicados.
  • Meter reglas de negocio en Silver en lugar de Gold.

Referencias

  • Medallion lakehouse architecture (Microsoft Learn)
  • Delta Lake tables in Fabric (Microsoft Learn)

SQL y Python juntos

Lo uso en mi trabajo

Problema

SQL es excelente para filtrar y agregar, y Python para automatizar y revisar. Casi siempre los necesitas juntos.

Conceptos

  • Deja que la base de datos haga el trabajo pesado (filtros y agregados).
  • Python recibe el resultado en un DataFrame para revisarlo, graficarlo o guardarlo.
  • Usa parámetros en las consultas, nunca texto pegado.

Diagrama

Python --consulta SQL (con parámetros)--> base de datos
Python <--------- DataFrame ---------------- resultado

Ejemplo

Con SQLite, que viene con Python, creo una tabla de ventas, la consulto con un parámetro y reviso el resultado en pandas. Funciona sin instalar nada más que pandas.

Código

import sqlite3
import pandas as pd

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE ventas (pais TEXT, monto REAL)")
con.executemany("INSERT INTO ventas VALUES (?, ?)",
                [("CO", 100), ("CO", 250), ("MX", 80)])

df = pd.read_sql(
    "SELECT pais, SUM(monto) AS total FROM ventas WHERE monto > ? GROUP BY pais",
    con, params=(90,))
print(df)

Qué deberías ver

  pais  total
0   CO  350.0

MX no aparece porque su única venta (80) no pasa el filtro monto > 90.

Errores comunes

  • Armar la consulta con f-strings: abre la puerta a la inyección SQL.
  • Traer toda la tabla a pandas y filtrar allá, en vez de filtrar en SQL.
  • Olvidar cerrar la conexión o confirmar los cambios.

Referencias

  • sqlite3 (Python docs)
  • pandas.read_sql

Nube: almacenamiento y permisos mínimos

En formación

Problema

Los datos de un pipeline necesitan un lugar en la nube, y quien los lee no debería poder borrarlos ni ver todo.

Conceptos

  • Cuenta de almacenamiento y contenedores: una por proyecto, con un contenedor por capa (bronze, silver, gold).
  • Mínimo privilegio: cada persona o servicio recibe solo el permiso que necesita.
  • Responsabilidad compartida: el proveedor cuida la infraestructura, tú cuidas datos y accesos.

Diagrama

Cuenta de almacenamiento
 ├─ contenedor bronze   (escribe: pipeline)
 ├─ contenedor silver   (escribe: pipeline)
 └─ contenedor gold     (lee: analistas)

Ejemplo

Creo una cuenta con espacio de nombres jerárquico y le doy a un analista solo permiso de lectura sobre gold.

Código

# Azure CLI (reemplaza los valores entre < >)
az storage account create -n <cuenta> -g rg-datos -l eastus \
  --sku Standard_LRS --kind StorageV2 --enable-hierarchical-namespace true

az storage container create --account-name <cuenta> -n gold --auth-mode login

az role assignment create --assignee <id-del-analista> \
  --role "Storage Blob Data Reader" \
  --scope /subscriptions/<sub>/resourceGroups/rg-datos/providers/Microsoft.Storage/storageAccounts/<cuenta>

Qué deberías ver

Cada comando devuelve un JSON con provisioningState: "Succeeded" o el rol asignado.

Pruébalo en una suscripción de práctica y borra el grupo de recursos al terminar, para no pagar de más.

Errores comunes

  • Dar el rol Owner o Contributor "para que funcione".
  • Dejar el acceso público abierto en un contenedor con datos.
  • Guardar llaves de acceso en el código en vez de usar identidades.

Referencias

  • Storage account overview (Microsoft Learn)
  • Shared responsibility in the cloud (Microsoft Learn)

Agentes de IA: herramientas y permisos

En formación

Problema

Un agente de IA no solo responde: ejecuta herramientas. Si alguien logra engañarlo con un texto, puede usar esas herramientas de forma peligrosa.

Conceptos

  • Inyección de prompts: instrucciones escondidas en datos que el agente lee.
  • Agencia excesiva: el agente tiene más herramientas o permisos de los que necesita.
  • Control: lista de herramientas permitidas, solo lectura por defecto y aprobación humana para acciones que cambian cosas.

Diagrama

Usuario / documento --> AGENTE --> [lista permitida] --> herramienta
                                  \--> acción que cambia datos --> aprobación humana

Ejemplo

Mi agente solo puede consultar ventas. Si un texto le pide borrar una tabla, la herramienta no existe en la lista y la acción se bloquea.

Código

# Capa de control entre el modelo y las herramientas (esquema)
PERMITIDAS = {
    "consultar_ventas": {"solo_lectura": True},
    "exportar_reporte": {"solo_lectura": False},   # cambia cosas
}

def ejecutar(nombre, args, aprobado_por_humano=False):
    if nombre not in PERMITIDAS:
        raise PermissionError(f"Herramienta no permitida: {nombre}")
    if not PERMITIDAS[nombre]["solo_lectura"] and not aprobado_por_humano:
        raise PermissionError("Requiere aprobación humana")
    return HERRAMIENTAS[nombre](**args)

Qué deberías ver

ejecutar("borrar_tabla", {})        -> PermissionError: Herramienta no permitida: borrar_tabla
ejecutar("exportar_reporte", {})   -> PermissionError: Requiere aprobación humana

Es un esquema de la idea, no un agente completo. Mi proyecto de AI Security lo va a probar con ataques reales.

Errores comunes

  • Confiar en que el prompt del sistema "prohíbe" algo: se controla en el código, no solo en el texto.
  • Darle al agente una cuenta con permisos de administrador.
  • No registrar qué herramientas usó, ni con qué argumentos.

Referencias

  • OWASP Top 10 for LLM Applications
  • Tool use with Claude (Anthropic docs)

Git desde la terminal: ramas y commits

Lo he aplicado en proyectos

Problema

Cambias un archivo, algo se rompe y no sabes qué fue lo último que tocaste. Git guarda cada cambio con un mensaje para poder volver.

Conceptos

  • Commit: una foto del proyecto con un mensaje que explica el cambio.
  • Rama: una copia de trabajo para probar sin tocar lo que ya funciona.
  • Push: sube tus commits a GitHub.

Diagrama

main  ●────●────────────●  (merge)
           \          /
feature     ●────●───●   (tu rama)

Ejemplo

Creo una rama para un cambio, reviso lo que voy a guardar, hago el commit y subo la rama a GitHub para abrir un pull request.

Código

git status                       # qué cambió
git switch -c feature/limpieza   # crear y entrar a una rama
git add -p                       # elegir qué guardar, por partes
git commit -m "Elimina duplicados en silver"
git push -u origin feature/limpieza
git log --oneline -5             # últimos commits

Qué deberías ver

[feature/limpieza 3f2a9c1] Elimina duplicados en silver
 1 file changed, 4 insertions(+), 1 deletion(-)

El código de 7 caracteres (3f2a9c1) es distinto en cada commit.

Errores comunes

  • Hacer commit directo a main sin probar.
  • Mensajes como "cambios" o "fix": en un mes nadie sabrá qué fue.
  • Subir contraseñas o llaves: agrégalas al .gitignore antes del primer commit.

Referencias

  • Pro Git (libro oficial)
  • GitHub Docs: about branches
